# 鉴权

系统有**两条互不相通的**鉴权入口，外加一类不属于鉴权的凭据存储。三者的用途、存法和泄漏后果都不同，不要混用。

## 三种秘密，三套机制

| | 管理员口令 | CI key | 凭据（Credential） |
| --- | --- | --- | --- |
| 谁在用 | 人，浏览器登录 | CI 流水线，机器调用 | 平台 CLI（微信/抖音等） |
| 需要取回原文吗 | **不需要**，只验证对不对 | **需要**，设置 → CI key 要随时复制 | **需要**，要交给 CLI 使用 |
| 存法 | scrypt 加盐哈希 | SHA-256 哈希（校验）+ 可逆加密（展示） | 可逆加密（`MASTER_KEY`） |
| 泄库后果 | 算不回原文 | 有 `MASTER_KEY` 时可解出 | 有 `MASTER_KEY` 时可解出 |
| 代码位置 | `src/shared/hash.ts` | `src/auth/store.ts` + `src/shared/crypto.ts` | `src/credentials/store.ts` |

**为什么口令用 scrypt、CI key 用 SHA-256**：人类口令熵低，必须用慢哈希顶住字典攻击；CI key 是 256 位随机值（或用户自定的足够长的值），而它出现在每次上报请求里，用慢哈希等于给自己的接口白加一道延迟。校验一律走哈希，展示走另一份可逆密文，两条路互不依赖。

## 路由与鉴权的对应

```
/healthz                     公开
/api/auth/state              公开（前端要知道该显示登录还是初始化）
/api/auth/password  POST     首次公开；设过口令后需要会话或当前口令
/api/auth/login     POST     公开
/api/ci/*                    CI key
/api/*                       管理员会话
```

两条入口刻意不互通，并有测试守住：

- CI key 不能访问 `/api/*`（返回 401）
- 会话 Cookie 不能访问 `/api/ci/*`（返回 401）

没有这条隔离，CI 日志里泄漏一个 key 就等于拿到整个后台的控制权。

## 管理员口令

单人使用，所以没有用户表，只有一行配置。

- 最短 8 个字符。
- 首次设置不需要任何凭据（系统刚起来时谁都没有口令，这是必然的初始窗口）。**部署后应立刻设置**。
- 设置之后再改口令，必须已登录或提供当前口令。
- 会话存在**进程内存**里，有效期 12 小时。重启后需要重新登录——单人场景下这个代价远小于为它建一张表。
- Cookie 带 `HttpOnly` 与 `SameSite=Strict`。

一处实现细节值得记下来：`scryptSync` 必须显式传 `maxmem`。Node 的默认上限是 32 MB，而 N=32768、r=8 的内存需求正好是 128·N·r = 32 MB，加上内部开销就会抛 `ERR_CRYPTO_INVALID_SCRYPT_PARAMS`。不传的话，第一次设置口令就会失败。实测 N=32768 约 44 ms。

## CI key

这是自用后台，不做「明文只显示一次」的仪式：值会一直保存，设置 → CI key 随时可以查看、复制和替换。

- 新建时可以直接填一个固定值，也可以留空自动生成 `mgc_<43 字符 base64url>`（32 字节随机）。
- 自定义值至少 8 个字符，不能包含空白；保存后可在列表里随时复制。
- 可以改名、换值（旧值立即失效）或**直接删除**（删掉即失效，列表里不留记录）。
- 可以保存多个，便于按流水线区分来源与单独删除。

**为什么删除而不是软删除**：一条既不能用、也不能改的「已吊销」记录留在设置页里只是噪音，而「它曾经存在过」对自用后台没有价值。要换值就直接改值，旧值当场失效，不必另留一条墓碑。

删除时，用它上报过的**构建记录不会被删**——那是 CI 上报的事实。只是那些记录不再知道当初由哪条 key 上报（`builds.ci_key_id` 置空）。
- 校验用 SHA-256 哈希，展示用另一份可逆密文：两者分别派生密钥，互不依赖。
- 从 v3 之前升级上来的旧记录没有密文，界面会提示「原文不可恢复，请换一个值」，不会假装能取回。

CI 侧两种传法都支持：

```bash
curl -X POST https://console.example.com/api/ci/builds \
  -H "Authorization: Bearer $CI_KEY" \
  -H "content-type: application/json" \
  -d '{ ... }'

# 或
curl -X POST https://console.example.com/api/ci/builds \
  -H "X-CI-Key: $CI_KEY" ...
```

校验是逐条定时安全比较，而不是按哈希索引查。库里只有个位数条目，而 SQL 的 `=` 会短路，可能泄漏前缀匹配长度。

## MASTER_KEY

凭据与 CI key 原文的加密主密钥，由部署方通过环境变量提供，至少 16 个字符。

**缺失或过短时进程拒绝启动**，不会生成临时密钥。因为临时密钥会让已有凭据在下次重启后全部解不开，而失败会发生在用户真正要发布的时候，那时才最难排查。

```bash
# 生成一个
openssl rand -base64 32
```

### 威胁模型（如实说明）

主密钥与数据在同一台机器上，这套加密防的是：

- 日志误打印
- 接口误回显
- 数据库备份文件泄漏

**不防主机被完全攻破**。攻击者拿到 shell 就能同时读到环境变量和数据库文件。这是单机部署不可消除的残余风险，不是 KMS 级隔离。
