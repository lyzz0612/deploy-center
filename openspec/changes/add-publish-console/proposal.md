# Proposal

## Why

同一款小游戏现在要同时发到微信小游戏、抖音小游戏和 H5，但三端的发布流程是割裂的：构建产物靠人手工拷贝和登记，H5 发版靠手动替换站点目录、回滚只能重新打包，各平台的 AppSecret、上传私钥散落在仓库 Actions Secrets 和个人机器上。微信/抖音的官方 CLI 又必须在能装 Node、有可写文件系统、有固定出口 IP 的常驻环境里跑，GitHub 托管 runner 的动态 IP 和境外网络让自动化上传反复卡住。

需要一套自己掌控的发布中控台：CI 只负责构建并上报产物，后台集中管理版本、凭据与发布动作；同时保证以后新增一个小游戏平台、或新增一种 H5 发布目标，都只需要写一个插件，而不是改核心代码。

## What Changes

- 新增 Docker 部署的中控台：单个 Node 进程承载中控台 UI、管理 API、CI 上报接口与长任务循环（发布、CLI 安装），数据与 CLI 各挂一个持久卷；后台不承担 H5 流量入口。
- CI 职责收缩为「构建产物 → 上报元数据」：上报内容是公开可访问的产物 URL、包类型、大小、sha256、commit 与描述，由 CI 侧自行保证链接可访问，后台不持有读取存储的凭据。
- 包类型（package type）作为纯数据在后台管理：新增一个包类型不需要改代码，只影响可选的发布目标。
- 发布目标类型（target kind）作为代码插件注册，提供环境检测、配置声明、发布阶段与执行体；新增平台或新增 H5 部署方式只需新增一个插件并在注册表加一行。
- 发布目标实例作为数据，按游戏配置，只引用凭据、不内联任何密钥；同一目标类型可有多个实例（不同 appid、不同账号、不同路径）。
- 凭据独立管理：凭据是有类型的加密键值袋，实例通过引用选择凭据，轮换只改一处。
- 发布建模为可重试的多阶段任务：每次发布产生一条不可变的历史记录，失败只重试失败阶段，回滚按目标类型声明的策略执行。
- 平台 CLI 可在后台安装、升级与探测（安装到持久卷，而非容器层），探测分「安装完好 / 凭据可用 / 平台可达」三层。
- 数据引用保护：没有引用的包类型、凭据、目标可以直接删除；被构建、目标或发布记录引用的则拒绝删除并列出引用来源。没有归档这一中间状态；删除游戏为级联删除，需输入 slug 确认。
- 单人使用，本版不引入多用户、RBAC 与操作审计；仅保留发布记录内的操作者字符串与完整日志。

## Capabilities

### New Capabilities

- `publish-console/game-catalog`: 多产品管理，以及作为纯数据维护的包类型登记簿；产物只允许上报到已登记的包类型。
- `publish-console/credentials`: 有类型的加密凭据的创建、轮换与引用保护；凭据不含明文落盘。
- `publish-console/build-ingestion`: CI 上报接口的鉴权、幂等与数据契约，以及构建产物在后台的可读视图。
- `publish-console/publish-targets`: 发布目标类型的插件注册表（声明接受哪些包类型、需要哪种凭据、具备哪些能力）与游戏级目标实例的配置。
- `publish-console/release-execution`: 发布任务的阶段编排、状态机、重试、回滚策略与结果校验。
- `publish-console/cli-management`: 平台 CLI 的安装、升级、版本共存与三层可用性探测。

### Modified Capabilities

无。仓库当前没有任何已存在的 spec。

## Impact

- 受影响系统：`minigames` 仓库从空仓库起步，本变更新增的是发布中控台本身；不修改任何既有代码。
- 部署影响：需要一个 Docker 主机（固定公网 IP）与两个持久卷——SQLite 数据库卷、`/opt/cli` CLI 安装卷。
- 构建侧影响：CI 需要在构建完成后新增一次上报调用，并保证产物 URL 在发布时仍可访问；该改动不在本变更内实施，本变更只定义接口契约。
- 运维影响：微信侧需要把主机出口 IP 加入代码上传密钥的白名单；抖音 CLI 是否能在 Linux 容器内运行尚未验证，是落地前必须先确认的外部不确定性。
- 明确不做：多用户与权限、操作审计、H5 反向代理、后台直连对象存储读取产物、平台审核状态的自动回调。
