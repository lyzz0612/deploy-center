# Spec Delta

## Purpose

维护多款小游戏的登记册与包类型清单，为构建上报和发布目标选择提供稳定的分类依据，并保证分类发生变化时不产生悬空引用。

## ADDED Requirements

### Requirement: 游戏登记册
后台 SHALL 维护一份小游戏登记册，每款游戏有不可变的 slug 作为唯一标识与可修改的显示名。slug 创建后 MUST 不可更改，因为它会出现在构建上报、发布目标与产物路径中。游戏 MUST NOT 有归档或停用状态：不要了就删除。

#### Scenario: 创建游戏
- **WHEN** 用户创建游戏并填写 slug "demo" 与显示名
- **THEN** 系统保存该游戏，并允许后续以 slug "demo" 绑定构建上报与发布目标

#### Scenario: slug 重复
- **WHEN** 用户创建游戏时使用了已存在的 slug
- **THEN** 系统拒绝创建并明确指出该 slug 已被占用

### Requirement: 删除游戏为级联删除
删除游戏 MUST 连带删除它名下的全部构建记录、发布目标与发布记录（含阶段日志）。该操作不可恢复，所以系统 MUST 在执行前要求用户输入该游戏的 slug 以确认，并 MUST 展示将被连带删除的条目数量。全局数据（包类型、凭据）MUST NOT 被游戏的删除带走。

#### Scenario: 级联删除游戏
- **WHEN** 用户删除一个有构建、目标与发布记录的游戏并正确输入其 slug
- **THEN** 该游戏及其名下构建、目标、发布记录与阶段日志全部删除，包类型与凭据不受影响

#### Scenario: 确认用的 slug 输错
- **WHEN** 用户点击删除但输入的 slug 与该游戏不一致
- **THEN** 系统拒绝删除，游戏及其名下数据不发生任何变化

#### Scenario: 删除前告知影响
- **WHEN** 用户打开某游戏的删除入口
- **THEN** 界面显示会连带删掉多少个目标、多少条构建与多少条发布记录

### Requirement: 包类型作为数据维护
包类型 SHALL 是后台可增删改的数据记录，除唯一标识与显示名外不携带任何影响系统处理产物的行为字段。新增一个包类型 MUST 不需要改代码。

#### Scenario: 新增包类型
- **WHEN** 用户在后台新增包类型 "qq"
- **THEN** 该类型立即出现在包类型列表中，并可被构建上报引用

#### Scenario: 无发布目标支持的包类型
- **WHEN** 某个包类型没有任何发布目标类型声明接受它
- **THEN** 后台在包类型列表中显式提示该类型当前无法发布

### Requirement: 包类型引用保护
没有被任何构建记录引用的包类型 SHALL 可以被直接删除；被引用的包类型 MUST NOT 被删除。系统 MUST NOT 提供归档这一中间状态。

#### Scenario: 删除被引用的包类型
- **WHEN** 用户尝试删除一个已被构建上报引用过的包类型
- **THEN** 系统拒绝删除，并说明存在引用的构建记录

#### Scenario: 删除没有引用的包类型
- **WHEN** 用户删除一个没有任何构建引用的包类型
- **THEN** 删除成功；若它是某个已注册插件声明接受的类型，下次启动时会被重新登记

### Requirement: 未登记包类型拒绝写入
系统 MUST NOT 创建指向未登记包类型的构建记录。

#### Scenario: 上报未登记包类型
- **WHEN** CI 上报的包类型在后台不存在
- **THEN** 系统返回 400 并说明该包类型未登记，不写入任何记录
